# Server-managed policy

These files document the reviewed policy installed on 157.228.114.185. CI deploys
application artifacts only. It does not install or execute uploaded host scripts.

Installed paths:

- `botkit-deploy`: `/usr/local/sbin/botkit-deploy`, root:root 0755.
- `ssh-gate`, `deploy-release`, `scheduled-backup`: `/usr/local/lib/botkit/`, root:root 0755.
- `pin-images.py` and the reviewed `scripts/backup.py`: `/usr/local/lib/botkit/`, root:root 0644.
- backup units: `/etc/systemd/system/`.
- ingress rules: `/etc/nftables.d/botkit-host.nft`.
- container forwarding rules: reviewed `deployment/botkit-guard.nft` installed by the administrator.

Root-owned `/etc/botkit/compose.yml` is based on the repository Compose, with all
host ports removed and `build.context` set to `${BOTKIT_REPO:?}`. Docker resolves
relative monitoring paths against the selected release directory. Credentials
are supplied with `--env-file /etc/botkit/compose.env`; there is no secret `.env`
inside release/build contexts. PostgreSQL/Redis/monitoring use separate internal
networks. Firewall rules cover forwarding as well as host input.

SSH Match policy forces `/usr/local/lib/botkit/ssh-gate` for `botkit-deploy`,
requires publickey, disables forwarding, user rc files and TTY. Its home and
`.ssh/authorized_keys` are root-owned. The only sudo entry permits
`/usr/local/sbin/botkit-deploy`; that program validates argument count and the
40-character lowercase revision before reading stdin, bounds archive sizes and
member counts, rejects links/unsafe paths, and serializes deploy/backup access.
It runs uploaded code only in containers under the fixed Compose configuration.

To update host policy, review the diff, install the affected files as root and
validate shell/Python, sshd, sudoers and nftables before reloading. A deployment
artifact cannot change this policy. Do not give the deployment user Docker group
membership or an unrestricted sudo command. Protect repository main and the CI
key: deployed application code can access the application's database and token.

The receiver's incoming archive is uncompressed tar, generated by `git archive`.
Release revision identifies the CI build; the SSH key authorizes deployment.
There is no separate signature verification of the archive against GitHub.
